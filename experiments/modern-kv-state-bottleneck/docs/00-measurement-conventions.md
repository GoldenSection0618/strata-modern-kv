# Measurement Conventions

This document defines the common measurement and comparison rules for the Modern KV / State Bottleneck Profiling experiments.

## 1. Token-length convention

`1K` means 1,024 tokens. The main context points are therefore 4,096, 8,192, 16,384, and 32,768 tokens.

The primary workload is text-only. Multimodal inputs are excluded from this experiment group so that vision/audio preprocessing does not confound cache/state measurements.

Because Qwen3.5 and Gemma 4 use different tokenizers, cross-model comparisons match token counts and workload structure rather than requiring identical raw text. Within each model, compared configurations reuse the same underlying request corpus or controlled token sequence whenever possible.

## 2. Cache-residency modes

The repository uses explicit cache-residency names instead of the ambiguous terms `warm cache` and `cold cache`.

### Recompute baseline

The reusable prefix is not restored from a cache tier. The request recomputes the prefix and suffix normally.

### GPU-resident hit control

The reusable prefix is already resident on GPU. This provides a lower-bound control for prefix reuse without CPU-GPU restore cost.

### CPU-resident hit

The reusable prefix is present in the CPU/offload tier and must be promoted to GPU before or during execution. This is the primary hierarchical-cache condition for the bottleneck experiments.

A run may be labeled as a CPU-resident hit only when the runtime counters or trace confirm that the intended cache/state groups were actually restored from CPU.

**Runtime-specific evidence.** The exact counters and per-request fields that satisfy these labels depend on the serving runtime. For the SGLang / HiCache path they are specified in [06-sglang-execution-path.md](06-sglang-execution-path.md) (§3–§5): public Prometheus deltas (`prefill_effective_tokens_total{mode=...}`, `load_back_tokens_total`, `hicache_backup_tokens_total`, `hicache_host_used_tokens`) are the required tier evidence; `meta_info.cached_tokens_details.{device,host}` is corroboration when the pinned runtime exposes it. A `cpu_hit` label requires a host-hit metric delta at least as large as the reusable prefix and no competing device-hit delta in the same isolated window; positive `load_back_tokens_total` is retained as corroboration. A missing metric is recorded as `null`/unsupported, never as a silent zero, and an overall cache hit rate alone never qualifies as `cpu_hit` evidence.

## 3. State accounting

Cache/state footprint must be measured from the serving runtime or profiler rather than inferred only from model formulas.

When available, report separately:

- full/global-attention KV;
- sliding-window/local-attention KV;
- recurrent or linear-attention state;
- allocator padding or other runtime overhead.

Aggregate cache/state memory may be reported after the component breakdown.

## 4. Transfer and stall accounting

`Transfer volume` is the number of bytes moved between CPU and GPU for the request or measurement interval.

`Transfer duration` is the observed DMA or transfer interval. It is a resource metric and may overlap with computation.

`I/O stall` is the non-overlapped latency attributable to waiting for required cache/state data. Only I/O stall is treated as an additive latency component.

The project must not add raw transfer duration to computation time when the two overlap.

## 5. TTFT decomposition

Client-observed TTFT is the primary latency metric.

For serving-load experiments, define:

```text
TTFT = queueing + service time
service time = compute-path time + non-overlapped I/O stall + other service overhead
```

The decomposition must avoid double counting asynchronous transfer time.

Two stall ratios are allowed, but their names must be explicit:

```text
service stall ratio = I/O stall / service time
TTFT stall contribution = I/O stall / TTFT
```

The service stall ratio is the preferred metric for deciding whether the execution path is becoming I/O-bound. TTFT stall contribution is useful for end-to-end impact under queueing.

## 6. Throughput and saturation

`Offered request rate` is the arrival rate generated by the workload driver.

`Achieved throughput` is the completed-request rate measured over the stable observation window.

`Sustainable capacity` is determined by a calibration run and is the highest load region in which achieved throughput continues to track offered load without a persistently growing queue. The exact operational threshold used in the implementation must be fixed before the final sweep and recorded with the results.

`Normalized load` is defined as:

```text
normalized load = offered request rate / measured sustainable capacity
```

## 7. Repetition and reporting

Each configuration includes warm-up followed by repeated measured runs.

Experiments 1 and 2 report at least median and P90 latency plus variability. Experiment 3 additionally reports P99 because tail latency is part of the load-saturation question.

Invalid runs are retained in raw results and excluded only with a documented reason.

## 8. Cross-model interpretation

Absolute matched comparisons use the same token lengths, prefix ratio, output length, cache-residency mode, and offered load whenever both models can sustain that configuration.

Near-saturation comparisons use normalized load and therefore do not claim identical absolute request rates.

Observed cross-model differences are descriptive and correlational unless an additional experiment isolates the architectural cause.
